## 1. ปัญหาและบริบทที่เสนอ

ใช้บริบท **เวิร์กช็อปภายในมหาวิทยาลัยที่มีที่นั่งจำกัด** เช่น เวิร์กช็อป Git สำหรับนักศึกษา ผู้จัดต้องการเผยแพร่กิจกรรมและเห็นรายชื่อผู้ลงทะเบียนที่เชื่อถือได้ ผู้เข้าร่วมต้องการหากิจกรรม ลงทะเบียน และกลับมาดูผลของตนโดยไม่ต้องถามผู้จัดทางแชต การลงทะเบียนผ่านระบบต้องไม่เกินจำนวนที่นั่ง แม้มีคำขอพร้อมกัน

| ผู้ใช้งาน | หน้าที่ |
|---|---|
| Organizer | เผยแพร่กิจกรรมของตนและดูรายชื่อผู้ลงทะเบียนของกิจกรรมนั้น ต่อไปจึงจัดการความจุ การปิดรับ และการเช็กชื่อ |
| Participant | ค้นดูหรือเลือกกิจกรรมที่เผยแพร่ ลงทะเบียน และดูผลของตนเอง ต่อไปจึงยกเลิกได้ตามกติกา |

Sprint 1 ใช้บัญชีและข้อมูลจำลอง ไม่ต้องทำ self-registration, password reset, ระบบชำระเงิน หรือระบบส่งอีเมลจริง ไม่มีบัญชีที่ถือสองบทบาทในร่างนี้ ไม่ทำ admin UI แยกหรือให้ผู้จัดเข้าถึงข้อมูลของผู้จัดคนอื่นโดยปริยาย

## 2. เส้นทาง Sprint 1 ที่เสนอ

1. Organizer เข้าสู่ระบบ กรอกชื่อ รายละเอียด วันเวลา สถานที่ และจำนวนที่นั่ง แล้วกดเผยแพร่ กิจกรรมปรากฏให้ Participant เห็นทันที ไม่ต้องมีสถานะ Draft หรือหน้าแก้ไขกิจกรรมใน Sprint 1
2. Participant เข้าสู่ระบบ เลือกกิจกรรมที่เผยแพร่ กดลงทะเบียน และเห็นผลในรายการของฉัน เมื่อโหลดหน้าซ้ำหรือเข้าสู่ระบบใหม่ต้องอ่านรายการเดิมจากฐานข้อมูลได้
3. Organizer เจ้าของกิจกรรมเปิดรายชื่อและเห็นข้อมูลเท่าที่จำเป็น เช่น ชื่อแสดงผลจำลอง ไม่แสดงรหัสผ่านหรือข้อมูลติดต่อโดยไม่มีเหตุผล
4. ผู้ใช้ทั้งสองบทบาทออกจากระบบได้ ผู้ไม่มี session ที่ใช้ได้เข้าถึงข้อมูลที่ต้องล็อกอินไม่ได้

วันเวลาเริ่มงานใน Sprint 1 ใช้เพื่อแสดงข้อมูล (เสนอ `Asia/Bangkok` ใน UI) ยังไม่ใช้เป็นเส้นตายปิดรับอัตโนมัติ ให้ใช้กิจกรรมในอนาคตในการสาธิต ทีมต้องยืนยันว่าจะยอมรับพฤติกรรมชั่วคราวนี้ก่อนเริ่ม หากจะเปลี่ยนเส้นทาง Sprint 1 จากตัวอย่างหัวข้อ 3 อย่างมีนัยสำคัญ ให้ขอความเห็นชอบจากอาจารย์/TA ตามข้อกำหนดรายวิชา

**ข้อเสนอด้านการออกแบบกฎความจุ:** ทำการตัดสินที่ฝั่ง API/ฐานข้อมูลด้วย transaction ที่คุมคำขอแข่งกันได้ เช่น ล็อกแถว Event ก่อนนับและสร้างรายการ หรือใช้กลไกจองแบบ atomic และบังคับ uniqueness ระดับฐานข้อมูลด้วย เมื่อเพิ่ม cancellation ให้รักษาประวัติและเงื่อนไขหนึ่งรายการที่ active ต่อคู่ Participant–Event วิธีเก็บสถานะ/constraint และการตอบเมื่อแข่งกันให้ตัดสินใน System-Level SDS และสัญญา F-03 ไม่ถือว่าการอ่าน `count` แล้ว `insert` โดยไม่มีการควบคุมการแข่งขันเพียงพอ

## 5. แนวทาง stack สำหรับให้ทีมยืนยัน

**ข้อเสนอ:** React + Vite สำหรับ UI, Express + TypeScript สำหรับ API, PostgreSQL สำหรับข้อมูลถาวร, Prisma สำหรับ schema/migration/การเข้าถึงข้อมูล เลือกเพราะทีมมีตัวอย่างใกล้เคียงและมี Node บนเครื่อง แต่ repo ทีมยังไม่ได้ใช้ stack นี้จริง ต้องให้ทั้งคู่ยืนยันก่อนกำหนดเวอร์ชันและคำสั่งติดตั้ง/run/build/test/migrate/seed

แยกสามชั้นทางตรรกะ ไม่จำเป็นต้องแยกหลายบริการ เสนอให้ UI และ API ใช้ origin เดียวกันเมื่อ deploy; เก็บ session ฝั่ง server ในที่เก็บถาวรพร้อม cookie ที่ตั้งค่าความปลอดภัยเหมาะสม กำหนด session expiry, logout, password hashing, การป้องกัน CSRF, ตัวแปร environment และข้อมูล seed ใน SDS/สัญญา F-01 ไม่ใส่รหัสผ่านจริงใน repo หรือเอกสาร เปิด Docker Engine หรือเลือกสภาพแวดล้อม PostgreSQL สำหรับพัฒนาและทดสอบในขั้นที่ได้รับอนุญาต ไม่ใช้ฐานข้อมูลจริงสำหรับการทดสอบอัตโนมัติ

## 7. เกณฑ์จบ S1-01 และเกณฑ์ส่งต่อ Lab 5

**S1-01 พร้อมส่งต่อเมื่อ:** ทั้งคู่ตกลง D-01 ถึง D-06, มีขอบเขต/ข้อยกเว้นที่ชัด, ทุกข้อกำหนดในร่างชี้ไปที่ feature และ Sprint และบันทึกความเห็นที่ยังไม่ลงตัวอย่างตรงไปตรงมา จากนั้นจึงทำ System-Level SDS และ feature contracts โดยแต่ละสัญญามี Feature-Level SDS, UI/API/data spec เท่าที่เกี่ยวข้อง, Acceptance Criteria, STS และ Definition of Done ก่อนเขียนโค้ดฟีเจอร์นั้น เก็บประวัติการเปลี่ยนแปลงและหลักฐาน red→green ของกฎสำคัญ

**Sprint 1 ส่งต่อ Lab 5 ได้เมื่อ:** ทำงานผ่าน Issue → feature/fix branch จาก staging → PR เข้า staging ที่เพื่อนร่วมทีมตรวจอย่างมีสาระ → integration tests → reviewed release PR เข้า `main` แล้วมี tag หรือ commit SHA ของ release ที่รันได้จริง บันทึก setup, คำสั่ง, ผลทดสอบ และเวอร์ชันที่ทดสอบให้ตรงกับ release; ถ้ามีผล fail/skip ให้รายงาน ไม่อ้างผลจาก commit อื่นหรืออ้างว่าอาจารย์ตรวจรับแล้วโดยไม่มีหลักฐาน การส่งต่อเป็น baseline สำหรับทำข้อกำหนด Lab 5 (Docker/CI/CD/deployment) ไม่ได้แปลว่า R-01–R-12 หรือ C-01–C-06 เสร็จแล้ว และไม่ใช่หลักฐาน deploy/ตรวจรับ

**บันทึกการปรับแผน v0.2:** เพิ่มผลลัพธ์/เกณฑ์ออกจากแต่ละ Sprint และแยกวัน checkpoint ของ Group Project ออกจากกำหนดส่ง Lab 5 โดยไม่เปลี่ยนการตัดสินใจ D-01 ถึง D-06 ดู [บันทึกการยืนยัน Sprint 1 v0.2](s1-02-system-level-sds.md)
