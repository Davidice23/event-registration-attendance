## 4. การเตรียมข้อมูลและการล้างข้อมูล

ระบบใช้ฐานข้อมูลจริงร่วมกันหนึ่งชุด และ Sprint 1 **ไม่มีการลบกิจกรรม แก้กิจกรรม หรือยกเลิกการสมัคร** ข้อมูลที่สร้างระหว่างทดสอบจึงล้างไม่ได้ เพื่อให้แต่ละ case ไม่พึ่งกัน:

1. ทุก case สร้างกิจกรรมใหม่ของตัวเอง ตั้งชื่อ `UAT-<ชื่อทีม>-<Case ID>-<HHMM>` เช่น `UAT-TeamX-01-1430` ชื่อไม่ซ้ำทำให้รันซ้ำได้โดยไม่ชนข้อมูลเก่า
2. ใช้วันเวลาเริ่มในอนาคต เช่น `2026-12-20 10:00` สถานที่ `UAT Room` และรายละเอียด `Synthetic UAT event`
3. **ห้ามสมัครหรือแตะกิจกรรม "Pun&Ice Lab 5 Persistence Test"** ซึ่งเป็นหลักฐานของ Lab 5
4. การสมัครของ Participant A/B จะสะสมในรายการของฉัน ให้ดูเฉพาะกิจกรรมที่ชื่อขึ้นต้นด้วย `UAT-` ของ case ที่กำลังทำ
5. หนึ่งเบราว์เซอร์ login ได้ครั้งละหนึ่งบัญชี เมื่อเปลี่ยนบัญชีให้กด **Sign Out** ก่อน หรือใช้หน้าต่าง private แยกต่อบัญชี

## 5. การบันทึกผล

ทุก case ให้บันทึก: Case ID, ชื่อผู้ทดสอบและทีม, วันเวลา, `commitSha` จาก `/api/health`, ข้อมูลที่กรอก, ผลที่เห็นจริง (ห้ามคัดลอกจาก expected) และ **PASS / FAIL / BLOCKED** ถ้า BLOCKED ให้บอกเหตุผล BLOCKED ไม่นับเป็น PASS

เก็บภาพหน้าจอที่เห็นแถบ URL อย่างน้อยสำหรับ UAT-01 และ UAT-03 และบังรหัสผ่านถ้าติดในภาพ

### UAT-02 — กฎธุรกิจและขอบเขต: จำนวนที่นั่ง, สมัครซ้ำ, กิจกรรมเต็ม

| หัวข้อ | รายละเอียด |
|---|---|
| ประเภท | Business rule / boundary |
| อ้างอิง | BR-01, BR-02, BR-03; AC-05, AC-08, AC-09 |
| จุดประสงค์ | ยืนยันว่าจำนวนที่นั่งต้องเป็นจำนวนเต็มตั้งแต่ 1, สมัครซ้ำไม่สร้างรายการเพิ่ม และกิจกรรมเต็มรับเพิ่มไม่ได้ |
| บทบาท | Organizer A, Participant A, Participant B |
| เงื่อนไขก่อนทดสอบ | ไม่มี session ค้าง |
| ข้อมูล | ชื่อ `UAT-<ทีม>-02-<HHMM>` วันเวลา/สถานที่/รายละเอียดตามหัวข้อ 4; จำนวนที่นั่ง `0` แล้วเปลี่ยนเป็น `1` |

| # | การกระทำ | ผลที่คาด |
|---|---|---|
| 1 | Sign In ด้วย Organizer A กรอกฟอร์มครบ แต่จำนวนที่นั่ง `0` แล้วกด **เผยแพร่กิจกรรม** | ระบบไม่เผยแพร่: เบราว์เซอร์เตือนที่ช่องจำนวนที่นั่ง หรือแอปแสดง "ตรวจชื่อ รายละเอียด สถานที่ เวลา และจำนวนที่นั่งให้ถูกต้อง (จำนวนที่นั่งต้องเป็นจำนวนเต็มตั้งแต่ 1 ขึ้นไป)"; **ไม่มี**การ์ดกิจกรรมชื่อนี้ในรายการ และไม่มีข้อความ "เผยแพร่กิจกรรมแล้ว" |
| 2 | เปลี่ยนจำนวนที่นั่งเป็น `1` แล้วกด **เผยแพร่กิจกรรม** | "เผยแพร่กิจกรรมแล้ว"; มีการ์ดกิจกรรมนี้ **หนึ่งใบ** จำนวนที่นั่ง `1` |
| 3 | Sign Out, Sign In ด้วย Participant A เปิดหน้า **กิจกรรม** ในสองแท็บของเบราว์เซอร์เดียวกัน (แท็บ 1 และแท็บ 2) | ทั้งสองแท็บเห็นกิจกรรมนี้พร้อมปุ่ม "สมัคร" |
| 4 | ในแท็บ 1 กด **สมัคร** | `สมัครกิจกรรม “<ชื่อ>” สำเร็จแล้ว`; ปุ่มเป็น "สมัครแล้ว" |
| 5 | ในแท็บ 2 (ยังไม่ reload) กด **สมัคร** ที่กิจกรรมเดียวกัน | `คุณสมัครกิจกรรม “<ชื่อ>” ไว้แล้ว ระบบไม่ได้สร้างรายการซ้ำ`; **ไม่ใช่**ข้อความ "เต็มแล้ว" |
| 6 | เปิด **รายการของฉัน** | กิจกรรมนี้ปรากฏ **ครั้งเดียว** |
| 7 | Sign Out, Sign In ด้วย Participant B แล้วกด **สมัคร** ที่กิจกรรมนี้ | `กิจกรรม “<ชื่อ>” เต็มแล้ว สมัครไม่สำเร็จ`; ปุ่มเป็น "เต็มแล้ว" และกดไม่ได้; หน้า **รายการของฉัน** ของ B ไม่มีกิจกรรมนี้ |
| 8 | Sign Out, Sign In ด้วย Organizer A เปิด **ดูรายชื่อผู้ลงทะเบียน** ของกิจกรรมนี้ | มี **หนึ่ง**รายการคือ `Participant A` ไม่มี Participant B |

การแย่งที่นั่งสุดท้ายพร้อมกัน (AC-09 ส่วน concurrency) ทดสอบด้วยมือให้เกิดพร้อมกันจริงไม่ได้ ครอบคลุมโดย automated test T-09 (ดูหัวข้อ 7)

## 8. การแจ้ง finding

เปิด Issue ใน <https://github.com/Davidice23/event-registration-attendance/issues> หนึ่ง Issue ต่อหนึ่งปัญหา ชื่อขึ้นต้นด้วย `[Lab 6 UAT]` และใส่:

- ผู้แจ้งและทีม, วันเวลา, `commitSha` ที่ทดสอบ
- Case ID และ AC ที่เกี่ยวข้อง, ข้อมูลก่อนทดสอบ (บัญชี, ชื่อกิจกรรม)
- ขั้นตอนทำซ้ำ, ผลที่คาด, ผลที่เกิดจริง
- ความรุนแรงที่เสนอ (Critical / Major / Minor) พร้อมผลกระทบต่อผู้ใช้
- ภาพหน้าจอ (บังรหัสผ่าน)

ถ้าเปิด Issue ไม่ได้ ส่งข้อมูลเดียวกันทางช่องทางที่ตกลงไว้ ทีมเราจะคัดแยกทุก finding และตอบใน Issue ว่าเป็น defect, duplicate, not-defect หรือ enhancement พร้อมเหตุผล
